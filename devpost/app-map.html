1. What Payee Check is

Payee Check helps owners and bookkeepers at small trades and construction firms in Waterloo Region verify a supplier's "our bank details changed" email. It holds the payment, guides a call-back to the number already on file, and locks what the supplier states before comparing it with what the email requested. It saves a dated, printable record of every attempt. (From the opening of devpost/prd.md.)

It runs entirely in the browser on fictional sample data: no sign-in, no server of its own (only the local Vite dev server), no other network calls and no AI model at run time. The screens follow one path: Overview → Request detail → Call-back step → Comparison → Verification record.

  • Kernel rules

    src/kernel/

    Plain TypeScript functions with no React and no storage: how values are normalised and compared (normalize.ts, compare.ts), what an attempt may do and which status it leaves (attempts.ts), records and masking (record.ts, mask.ts), and the checks on loaded data (invariants.ts).

  • Store

    src/storage/store.ts

    The only code that touches localStorage. One key, payee-check:v1; each action writes the whole state once and reads it back. Loaded data must pass a zod schema (schema.ts) and checkInvariants before anything is shown.

  • App state hook

    src/app/useAppState.ts

    Turns button presses into kernel calls and enforces "save first, show second": compute, save, read back, and only then change the screen.

  • Router

    src/app/routes.ts

    A small hash router: #/, #/request/<id>, …/call, …/compare, #/record/<id>. Its guards read the kernel's phaseOf, so it can't open a screen the kernel would refuse.

  • Screens

    src/screens/ and src/App.tsx

    Overview, RequestDetail, CallbackStep, Comparison and RecordView; App.tsx picks one per route. Interface wording comes from src/copy.ts.

  • Sample data

    src/data/samples.ts

    Five fictional suppliers, five payments and two bank-change requests: req-mismatch (Harbourline Lumber Ltd., should stay held) and req-legit (Cedarline Electrical Supply Inc., should verify).

2. One action, end to end: pressing Compare

The Harbourline sample: the supplier states an account ending 4471, while the email requested one ending 9020.

The code that makes it "save first, show second"

src/app/useAppState.ts, inside compare (exact excerpt)

if (!store.save(result.state).ok) {
  failed(() => {
    run()
  })
  return { ok: false }
}
commit(result.state)
navigate({ name: 'compare', requestId })
return { ok: true }

src/storage/store.ts, save (exact excerpt)

save(state) {
  try {
    const raw = JSON.stringify(state)
    const storage = getStorage()
    storage.setItem(STORAGE_KEY, raw)
    return storage.getItem(STORAGE_KEY) === raw ? { ok: true } : { ok: false, error: 'readback' }
  } catch (error) {
    return { ok: false, error: isQuotaError(error) ? 'quota' : 'unavailable' }
  }
},

3. Reference route: follow Compare through the code

Reference route

A suggested reading order for the action above, three stops long. It was not walked through as a guided tour. Open a file by name (Ctrl+P in VS Code), then search inside it (Ctrl+F) for the anchor. Line numbers are from this snapshot.

  1. Stop 1 The button: src/screens/CallbackStep.tsx

    Search for handleCompare (near line 62).

    Compare calls onCompare(answers) with what was typed, which lives only in this component's state. If the reply names missing fields, it shows the "Compare needs every answer" summary and moves focus to it; on success the hook has already moved on to the Comparison. (src/App.tsx wires this up: search app.compare.)

  2. Stop 2 The order of events: src/app/useAppState.ts

    Search for const compare = (near line 118).

    The kernel first (lockAndCompare with one clock reading), then store.save, and only if that succeeds commit and navigate. A failed save leaves the screen as it was and shows "Couldn't save—nothing was changed." with Try again.

  3. Stop 3 The rules: src/kernel/attempts.ts

    Search for lockAndCompare (near line 78), then paymentStatusOf (near line 56).

    lockAndCompare decides whether this attempt may lock and builds it: verified or pending requests are refused, then blank answers, then compareDetails runs and a 'compared' attempt is appended. paymentStatusOf explains the Overview afterwards: status comes only from saved attempts, so the payment stays on hold until Save attempt.

4. To change this, start here

  • Wording on any screen

    src/copy.ts holds the interface strings (BUTTONS, STATUS, DETAILS_MATCH and the rest). Tests type the expected strings out literally and never import this file, so a wording change also means updating the test that checks it. That is deliberate: the app and its test can't share a typo.

  • Sample suppliers, payments and emails

    src/data/samples.ts. The fiction rules (every domain ends in .example, phones stay in 519-555-0100 to 0199, invented names, institution numbers that avoid well-known real ones) are tests in src/data/samples.test.ts under describe('fiction rules'; keep them passing.

  • What counts as a match

    src/kernel/normalize.ts (normalizeNumber, normalizeName, isBlank) and src/kernel/compare.ts (compareDetails, comparisonLine). Their case tables are normalize.test.ts and compare.test.ts, whose rows carry the IDs CR-1, CR-3 to CR-6 and CR-8 from the Verification Map.

  • Statuses, and when a new attempt may start

    src/kernel/attempts.ts: phaseOf (the request's phase, from the order attempts were added), paymentStatusOf (saved attempts only) and canStartAttempt. The guard in src/app/routes.ts reads the same phaseOf, so the screens follow.

  • Look and print

    src/styles.css: colour, spacing and font tokens on :root, and the @media print rules for the printed record. src/look.test.ts checks the tokens and the contrast of each colour pair.

  • A new requirement

    Add a row with a new ID to the Verification Map in devpost/spec.md, starting its Unit or E2E cell with the test file's short name in backticks (such as `attempts`), and raise the count in the "54 IDs: …" line under the table. Then write a test in that file whose title starts with that ID. src/traceability.test.ts reads the map and every test title and fails until they agree. One ID runs alone with npx vitest run -t "CR-3" or npx playwright test -g "CR-3".

5. A practice to reuse: one rule, its ID, two tests, one deliberate break

How this project checks that a rule is really enforced, shown on the rule that matters most: a match on screen must not release a payment by itself.

  1. The decision

    An unsaved match must leave the payment held.

    devpost/prd.md › Outcomes and payment status; Verification Map row OS-1 in devpost/spec.md. In code: paymentStatusOf reads only saved attempts.

  2. Proof at two levels

    Unit: tests titled "OS-1 …" in src/kernel/attempts.test.ts, such as 'OS-1 an unsaved verified comparison leaves the payment "On hold—verification needed"'.

    End to end: tests/e2e/verified-journey.spec.ts, 'OS-1 a match reads "Details match." and stays on hold until saved, then Verified and Ready to pay'.

  3. The deliberate break, B-3

    Status derived from the latest attempt, saved or not (paymentStatusOf read attemptsFor(…).at(-1)). Both levels went red: the unit tests got "Ready to pay" instead of "On hold—verification needed", and the Overview row did too (verified-journey.spec.ts:136). Reverted, then green again.

    Logged in devpost/checklist.md › Revisions with B-1 to B-9.

  4. What it shows

    A passing test counts only if it could have failed. The pass also shows which level catches what: B-5 (an email contact drawn as a link) was caught end to end, not by the guards unit test.

To reuse it on another project

  1. Give every acceptance criterion a short, stable ID (here a section prefix and a position, such as OS-1 or CR-3).
  2. Start every test title with the IDs it proves, so one criterion can run on its own.
  3. Check the mapping with a test, as src/traceability.test.ts does against the table in devpost/spec.md, so the map can't claim coverage that no longer exists.
  4. Break each core rule once by hand, run only its ID, confirm it fails on the expected assertion, revert, and log the break, the failing test and the first failure line. If a break doesn't fail, fix the test first.
The rule in code: src/kernel/attempts.ts

Exact excerpt (two separate spots in the file)

const latestSaved = (state: PersistedState, requestId: string): Attempt | undefined =>
  attemptsFor(state, requestId)
    .filter((a) => a.status === 'saved')
    .at(-1)

// Status comes only from saved attempts, so an unsaved or abandoned comparison can never release a payment.
export function paymentStatusOf(state: PersistedState, requestId: string): PaymentStatus {
  const saved = latestSaved(state, requestId)
  return saved ? savedStatusFor(saved.outcome) : STATUS.needsVerification
}

6. Run it again

Needs Node 22.12 or newer. From the project folder, one command per line:

npm install
npm run dev

Then open http://localhost:5180 (the port is fixed in vite.config.ts). Reset demo on the Overview clears only the payee-check:v1 key and brings back the starting sample data.

npm run check

Runs the type check, the Vitest unit tests, then the Playwright end-to-end tests in the installed Google Chrome. On Oct 26, 2026 it passed with 470 unit tests and 59 end-to-end tests (README.md › Run the checks).
